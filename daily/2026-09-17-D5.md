## 一、为什么需要索引？（设计哲学）

### 1.1 没有索引：全表扫描

```sql
SELECT * FROM items WHERE grp = 42;   -- 10000 行里找 100 行
```

没目录怎么办？**从第 1 行翻到第 10000 行**，一行一行看 grp 是不是 42。
查询计划里这个词叫 `SCAN`（扫描）。10 行无所谓，1000 万行就是灾难。

### 1.2 索引 = 书的目录

书 1.5 万页，找"事务"在哪：你不会从第 1 页翻起，而是**先查目录**（"事务 …… p79"），
直奔第 79 页。目录的特点：
- 按标题**排好序**（好二分查找）；
- 每条只记**标题 + 页码**（很薄，翻得快）；
- 正文不动，目录是**额外**的一份结构。

数据库索引一模一样：
- 按搜索键**排好序**；
- 每条只记**键 + 行在哪**（行定位符/主键）；
- 数据文件不动，索引是**额外**的文件（所以索引文件通常比数据文件小）。

> [!quote] 教材原话（书 17 页）
> "To locate a record, database systems use indexes: auxiliary data structures
> that allow it to efficiently locate data records **without scanning an entire table**
> on every access."（索引就是为了**不每次都全表扫描**。）

### 1.3 代价：天下没有免费目录

- **占空间**：目录本身要纸。
- **写变慢**：正文每改一处，目录也要同步改。`INSERT/UPDATE/DELETE` 都要维护索引。
- 所以索引只建在**常查的列**上，不是每列都建。

## 二、为什么是 B 树？（磁盘逼的）

### 2.1 内存里好好的二叉搜索树，搬到磁盘就烂

二叉搜索树：左小右大，查找二分，很漂亮。但它假设**每次比较都一样快**（内存）。
磁盘不一样：**读 1 个字节和读 4KB 花的时间几乎一样**（一次块传输）。

两个后果：
1. **高度 = 寻道次数**。100 万行的二叉树高约 20 层，最坏要 20 次磁盘寻道。
   机械盘一次寻道按毫秒算，20 次就是几十毫秒——一次查询，太慢。
2. **局部性差**。随机插入的节点散落在磁盘各处，父子指针跨好几个页，
   读一个节点要抓好几块（书 28 页）。

### 2.2 解药：又矮又宽

```
fanout（分叉数）越高 → 高度越矮 → 寻道次数越少
```

- 二叉树：每节点 1 个键、2 个孩子 → 100 万行要 ~20 层。
- B 树：每节点几百个键、几百个孩子 → 100 万行只要 **3 层**（3 次寻道）。
- 每一层正好读**一页**（一页 = 一次磁盘传输，不浪费）。

> [!quote] 教材原话（书 28–32 页）
> "a version of the tree better suited for disk has to exhibit: high fanout…
> low height… Fanout and height are inversely correlated."
> B 树 = 图书馆目录室：先找对柜子，再找对架子，再找对抽屉，最后翻卡片。
> （书 33 页原比喻，一层比一层精确。）

### 2.3 三个旋钮（书 21–22 页，全书通用）

| 旋钮 | 意思 | B 树的选择 |
|------|------|-----------|
| Buffering 缓冲 | 先在内存攒一批再写盘？ | 按页读写，批量传输 |
| Mutability 可变性 | 原地改还是追加写？ | 原地改（mutable，D9 的 LSM 反着来） |
| Ordering 有序性 | 按键排好还是按插入顺序？ | 按键排好（范围查询快） |

### 2.4 设计哲学（一句话 + 四条）

> [!quote] 一句话
> **数据结构是硬件的形状。磁盘按块传输、寻道贵，B 树就长成"块"的样子。**

1. **按传输单位设计**：磁盘一次读一页，节点就做成一页大。一页读进来，里面几百个键随便二分，不再读盘——**不浪费每一次寻道**。
2. **用宽度换高度**：高度 = 寻道次数，是最贵的账。把节点做宽（高 fanout），
   100 万行压到 3 层，用"每页多装"换"少跑几趟"。
3. **有序是免费的导航**：键排好序，二分定位 + 范围连扫都是顺带的。
   无序能省插入的功夫，但每次查找都要翻全页——B 树选择"插入时多做一点，查找永远快"。
4. **接受一半空**：节点预留空间给未来插入，空间利用率最低 50% 也接受。
   用空间换"少分裂"：树平时只横向长，分裂传到根才长高一层，
   平衡的维护成本被摊薄到每次插入一点点。

反例对照：二叉搜索树是"内存的形状"（每次比较等价），硬搬到磁盘就是削足适履。
D9 的 LSM 则是另一套哲学（SSD 时代 + 写优先），到时再对比。

## 三、B 树长什么样？

```
            ┌──────────┐
            │    5     │  ← 根：1 个键，2 个指针
            └────┬─────┘
        ┌────────┴────────┐
   ┌────┴────┐       ┌────┴────┐
   │  2 │  3 │       │  7 │  9 │  ← 叶：存键+值
   └─────────┘       └─────────┘
```

- **三层人**：根（没爹）→ 中间节点（传话）→ 叶（没娃，存真实数据）。
- **每节点**：最多 N 个键 + N+1 个指针；键**从小到大排好**（才能二分）。
- **分隔键**：`5` 的意思是"左边子树全 < 5，右边全 ≥ 5"，是路牌不是数据。
- **B+ 树**（数据库实际用的，书 36 页）：值**只存叶层**，中间层只存路牌。
  查找永远走到叶，插入删除也只动叶（除非分裂/合并往上传）。

## 四、手工推演 1：查找 7（每次只读一页）

在上面的树里找 `7`：

1. 读**根**（第 1 次磁盘读）：键是 [5]。7 ≥ 5 → 走**右指针**。
2. 读**右叶**（第 2 次磁盘读）：键是 [7, 9]，二分一下 → 找到 7，拿值。
3. 结束。**2 次寻道**，与树高相等（根→叶 2 层）。

规律：**查几次盘 = 树几层**。B 树 3 层存 100 万行，所以点查最多 3 次寻道。
（比较次数是另一笔账：每节点内二分，是 log₂ 级别。寻道看层数，比较看二分——书 37 页。）

## 五、手工推演 2：插入 15 引发分裂（书图 2-11 思路）

设每节点最多 2 个键。叶节点 `[10, 20]` 已满，新来 `15`：

1. 先按查找走到该叶，排序插入 → `[10, 15, 20]`，**超了（overflow）**。
2. **申请一个新节点**，把一半搬过去：左留 `[10]`，右搬 `[20]`。
3. 中间的 `15` **晋升（promote）**成父节点的分隔键：父节点记下"＜15 走左，≥15 走右"。
4. 如果父节点也被撑满 → 父节点跟着分裂，一路向上传；传到根、根也满 →
   根分裂、新根诞生，**树长高一层（全树唯一长高的时刻）**。

四步口诀（书 39 页）：**申请新节点 → 搬一半 → 放新元素 → 父节点记路牌**。
删除反过来：太空了（underflow）就和邻居**合并**，三步：右搬左 → 删父指针 → 删右节点。

## 六、10000 行实验（实测）

数据：`items` 表 10000 行，`grp = i % 100`（100 组，每组 100 行）。查 `grp = 42`。

| | 查询计划 | 含义 | 500 次耗时 |
|---|---|---|---|
| 建索引前 | `SCAN items` | 全表翻 10000 行 | 0.144s |
| 建索引后 | `SEARCH items USING INDEX idx_items_grp (grp=?)` | 查目录直达，只碰目录+100 行 | 0.031s |

- 结果都是 100 行：**正确性不变，变的只是找法的代价**。
- 约快 4.6 倍；数据量越大、查得越 selective，差距越大。
- 代价：索引占空间；写操作要同步改目录。

### 查询计划两词经

- `SCAN 表名` = 翻全表（没目录）。
- `SEARCH 表名 USING INDEX 索引名` = 走目录。
- D1–D4 的小表全是 SCAN（几行，翻就翻了）；以后看到 SCAN + 大表，就该问"要不要建索引"。

## 七、代码例子 1：手写迷你 B 树（可运行 `labs/sql/learn_day05_btree.py`）

设定：t=2，每节点最多 3 个键。插入 `10, 20, 5, 6, 15, 12, 17`，程序一步一步打印：

```
插入 10 → 叶 [10]
插入 20 → 叶 [10, 20]
插入 5  → 叶 [5, 10, 20]（满了）
插入 6  → 根满了，分裂根，树长高一层；中间键 10 晋升；
          左 [5]，右 [20]；6 进左叶 → [5, 6]
插入 15 → 右叶 [15, 20]
插入 12 → 右叶 [12, 15, 20]（满了）
插入 17 → 分裂 [12, 15, 20]，15 晋升；左 [12]，右 [20]；
          17 进右叶 → [17, 20]
```

最终的树：

```
[10, 15]
  [5, 6]
  [12]
  [17, 20]
```

查找 `6` 走一遍（对照第四节）：

```
看节点 [10, 15]：找 6 → 6 < 10，往下一层走
  看节点 [5, 6]：找 6 → 命中！
```

查找 `7`（不存在的）：

```
看节点 [10, 15]：找 7 → 往下走
  看节点 [5, 6]：找 7 → 到叶了还没有，7 不存在。
```

自检：7 个插入的键全找到；7 和 100 确认不存在。
注意：教学版键值放一起；真实数据库多用 B+ 树（值只放叶层）。

## 八、代码例子 2：10000 行实验（可运行 `labs/sql/learn_day05.py`）

```python
# 造 10000 行：grp = i % 100，共 100 组，每组 100 行
conn.executemany(
    "INSERT INTO items (id, grp, val) VALUES (?, ?, ?)",
    [(i, i % 100, (i * 7 % 1000) / 1000.0) for i in range(10000)],
)

# 建索引前：EXPLAIN QUERY PLAN → SCAN items（翻全表），500 次 0.144s
# 建索引：CREATE INDEX idx_items_grp ON items(grp)
# 建索引后：→ SEARCH items USING INDEX idx_items_grp (grp=?)，500 次 0.031s
# 结果都是 100 行。结论：正确性不变，耗时约快 4.6 倍。
```
