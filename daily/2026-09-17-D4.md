## 一、为什么需要事务？（设计哲学）

### 1.1 先看没有事务会怎么烂

开一个 run 要写**两步**：① 建 run，② 写它的 accuracy。
如果第 ① 步提交了，第 ② 步失败（值非法、程序崩了），库里留下**run 6 有记录、没指标**——孤儿数据。

实测（learn_day04 例1）：分开提交后，孤儿 run = run 3、run 5（本来就没指标）**+ run 6（新建的，指标没写进去）**。

生活类比：**银行转账**。
- 第 ① 步：A 扣 100。
- 第 ② 步：B 加 100。
- 如果 ① 成功、② 失败（断电了），100 块凭空消失。银行绝不能让这种事发生。

> [!quote] 设计哲学
> **现实中的一件事，经常要拆成多个数据库操作。但对外，它必须是一个整体：
> 要么全生效，要么全没发生，不许一半。**
> 这个"整体"就叫**事务（transaction）**。

### 1.2 事务三件套

```python
conn.execute("INSERT INTO runs ...")      # 第 1 步
conn.execute("INSERT INTO metrics ...")   # 第 2 步
conn.commit()    # 两步都成功 → 一起生效
# 或
conn.rollback()  # 任何一步失败 → 一起撤销，当没发生过
```

| 操作 | 意思 | 生活类比 |
|------|------|---------|
| 自动开始 | 第一条写操作执行，事务就开始了（不用手写 BEGIN） | 拿起笔，账本翻开 |
| `commit()` | 提交：两步一起生效，所有人可见 | 落笔、盖章 |
| `rollback()` | 回滚：两步一起撤销 | 把这页撕了，当没写过 |

### 1.3 实测：回滚后什么都没发生

同一个事务插 run 6 + 它的 accuracy，第二步失败 → rollback。
结果：runs 还是 5 个，metrics 还是 6 条，run 6 从没存在过。（learn_day04 例2）

两步都成功 → commit，run 6 和 accuracy 0.90 一起出现，谁也不落单。（例3）

## 二、ACID（教材原话 + 人话翻译）

> 来源：书 79–80 页（PDF 99–100 页）。"A transaction is an indivisible logical unit of work…
> allowing you to represent multiple operations as a single step."

| 字母 | 原文 | 人话 | 我们的例子 |
|------|------|------|-----------|
| **A** Atomicity 原子性 | 事务不可分：全成功或全不做；commit 让修改可见，abort 回滚副作用 | 转账不能只扣不加；run+metric 要么一起有，要么一起没有 |
| **C** Consistency 一致性 | 事务只能把库从一个合法状态带到另一个合法状态（约束、外键不断） | 外键/CHECK 约束永远成立；这是唯一**用户也要负责**的属性 |
| **I** Isolation 隔离性 | 并发事务互不干扰，好似串行执行；何时可见由隔离级别定 | 没 commit 前，别人看不见我的修改（例4实测：我见 6 个，别人见 5 个） |
| **D** Durability 持久性 | commit 后修改落盘，断电宕机不丢 | commit = 落盘保证（底层靠日志，D8 学 WAL） |

> [!note] C 最特殊
> 原文说它是"定义最弱的属性"，因为它是**唯一用户也要负责的**：
> 数据库保证机制（A/I/D），但"什么算合法"（约束怎么写、事务边界划在哪）由你定。
> 约束写错了，数据库照样"一致地"存错数据。

### 四个属性住在图 1-1 的哪儿？

- A（原子性）：commit/rollback 机制（事务管理器）。
- I（隔离性）：锁管理器（第 5 章后面 + D8）。
- D（持久性）：恢复管理器 + 日志（D8 WAL）。
- C：到处都是（约束 + 你的事务划分）。

## 三、带注释的代码例子（5 个，可运行 `labs/sql/learn_day04.py`）

### 例 1：没有事务，一半成功留垃圾

```python
conn.execute("INSERT INTO runs ... VALUES (6, 1, 'CNN', 9, ...)")
conn.commit()   # 第一步先提交，退不回来了
conn.execute("INSERT INTO metrics ... VALUES (6, 'accuracy', -1.0)")
# 非法值！违反 CHECK(metric_value >= 0)，被数据库拒绝：
# IntegrityError: CHECK constraint failed: metric_value >= 0

# 查孤儿 run（LEFT JOIN + IS NULL，D2 套路）：
# 输出：(3,)、(5,)、(6,) —— run 6 成了新建的孤儿
```

### 例 2：事务 + 回滚（D4 必做实验）

```python
try:
    conn.execute("INSERT INTO runs ... VALUES (6, ...)")
    conn.execute("INSERT INTO metrics ... VALUES (6, 'accuracy', 0.90)")
    raise RuntimeError("模拟第二步失败")
    conn.commit()      # 走不到这里
except RuntimeError:
    conn.rollback()    # 两步一起撤销
# 验证：runs=5（应为5），metrics=6（应为6）。run 6 从没存在过。
```

### 例 3：事务 + 提交

```python
conn.execute("INSERT INTO runs ... VALUES (6, ...)")
conn.execute("INSERT INTO metrics ... VALUES (6, 'accuracy', 0.90)")
conn.commit()   # 两步一起生效
# 查：(6, 'CNN', 0.9) —— run 和指标一起出现
```

### 例 4：没提交，别人看不见（隔离性初体验）

```python
c1 = sqlite3.connect(path)   # 我
c2 = sqlite3.connect(path)   # 别人
c1.execute("INSERT INTO runs ... VALUES (6, ...)")
# c1 还没 commit：
c1 查 runs → 6 个（我看得见自己的修改）
c2 查 runs → 5 个（别人看不见）
c1.rollback()
c2 查 runs → 还是 5 个（run 6 从没存在过）
```

### 例 5：Python sqlite3 事务三规则（背下来）

1. 第一条 INSERT/UPDATE/DELETE 执行时，事务**自动开始**（不用手写 BEGIN）。
2. `commit()` 之前，修改只对本连接可见；崩了/rollback 就全撤销。
3. **忘了 commit 就关连接 = 自动 rollback，白干。**SELECT 不开事务。

参数绑定老规矩：`?` 占位符传值，不用 f-string 拼 SQL。
