## 一、为什么用二进制？（设计哲学）

同一条记录（key=user:1001, value=Tom）：**JSON 36 字节，二进制 28 字节**。
JSON 的钱花在字段名、引号、括号这些元数据上；二进制只存"长度+内容"。

> [!quote] 三个理由
> 1. **紧凑**：不存字段名，存位置（第几个字节是什么，事先约好）。
> 2. **可算偏移**：长度已知，切片一次到位，不用扫描找边界。
> 3. **可验算**：尾巴带校验和，坏了认得出。

为什么不用 pickle？Python 专有（换语言读不了）、能执行任意代码（收坏文件=中招）、
体积大。数据库要的是**跨语言、透明、可控**的格式。

## 二、记录长什么样？（v1 格式）

```
+--------+---------+--------+----------+----------+-----+-------+-------+
| magic  | version | optype | key_len  | val_len  | key | value | crc32 |
| 2B     | 1B      | 1B     | u32BE    | u32BE    | ... | ...   | u32BE |
+--------+---------+--------+----------+----------+-----+-------+-------+
```

实测解剖（key=ab, value=XY，共 20 字节）：

```
hex：4d4b 01 01 00000002 00000002 6162 5859 c33d044
     ~~~~ ~~ ~~ ~~~~~~~~ ~~~~~~~~ ~~~~ ~~~~ ~~~~~~~
     MK   v1 PUT key长=2 val长=2  ab   XY   crc32
```

- magic `MK`：文件身份证，走错文件秒发现。
- version：以后改格式，新老 reader 靠它分流（Cassandra 甚至写文件名里）。
- optype：1=PUT，2=DELETE（墓碑，val_len=0）。
- 空 value `b""` 合法：有记录但值是空 ≠ 没有记录。

## 三、长度前缀（Pascal 式）

```python
# 存：先写长（4 字节），再写内容
# 读：先读长 n，再切 n 字节 → O(1)，一次到位
```

对比 C 语言 `\0` 结尾：每次现找 0，O(n)；内容里还不能有 0。
实测：`b'a\x00b'`（中间带 0）存取完整——长度前缀不在乎内容是啥。

## 四、大小端（多字节整数的字节顺序）

`0x01020304` 存成 4 字节：

```
大端 BE：01 02 03 04（高位在前，好读，网络惯例）→ 我们选它
小端 LE：04 03 02 01（低位在前，x86 内存序）
```

规则只有一条：**编解码用同一种**。`struct` 的 `>`（BE）和 `<`（LE）别混。

## 五、校验（检错，不纠错）

- 写时对 magic..value 算 crc32 存尾；读时重算比对。
- 实测改 1 个 bit：存 `0xb8e8c1d9` vs 算 `0x7442c147` → 拒收。
- 教材区分：checksum（求和/XOR，只能抓单 bit）vs CRC（抓连续多 bit 坏，存盘主流）。
- CRC **不是安全机制**：防手滑断电，不防黑客（防篡改要用密码学哈希）。

## 六、截断认得出（D10 恢复的前菜）

长度头说要 117 字节，实际只剩 114 → **尾部没写完**，报截断。
恢复时就靠这个认"最后完整边界"：完整之前的全要，残尾处理掉再写。

## 七、偏移链（日志扫描雏形）

`decode_record` 返回 `next_offset`：一条的终点是下一条的起点。
多条连着解 = 日志扫描，MiniKV 启动重建索引就这么走（D9/D10）。
